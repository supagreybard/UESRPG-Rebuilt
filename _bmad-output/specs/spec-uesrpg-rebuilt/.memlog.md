- (decision) Spec distills existing BMad planning artifacts for UESRPG Rebuilt 1.0; PRD, rules checklist, UX spines, architecture spine, and project context remain adopted companions where detail is load-bearing.
- (capability) CAP-1: UESRPG groups can install and run the Foundry VTT 14 system package with native document, sheet, roll, chat, combat, compendium, tutorial, and packaging behavior.
- (capability) CAP-2: Players and GMs can view, edit, and use character, statblock, item/equipment, and magic documents for preparation and live play.
- (capability) CAP-3: Users can resolve core d100 tests and transparent roll output for skill, characteristic, opposed, combat, spellcasting, mishap, and related workflows.
- (capability) CAP-4: Users and Greybard can create valid editable Foundry documents through required builders and minimal manual-supported workflows where 1.0 permits fallback.
- (capability) CAP-5: The package can ship broad rights-cleared System Content through managed compendium sources and manifest-grade provenance review.
- (capability) CAP-6: Release readiness can be demonstrated through baseline automated checks, Foundry runtime validation evidence, onboarding/tutorial support, and a balanced one-shot minimal-handholding pass.
- (constraint) Implementation must remain Foundry-native for Foundry VTT 14, TypeScript strict, localized, Vite-packaged, and aligned across package metadata, registrations, data models, sheets, templates, styles, migrations, and build-copy rules.
- (constraint) Prepared user-facing package content must not be AI-generated and distributed System Content requires rights/provenance review through a machine-readable manifest.
- (constraint) Rules automation must be transparent, shared-service based, conservative in document updates, and visibly support manual fallback where 1.0 permits it.
- (decision) Non-goals include replacing Foundry paradigms, shipping unclear-rights or AI-generated prepared content, building a generic Elder Scrolls database, and treating build success as runtime validation.
- (assumption) Minimal-handholding validation may initially be Greybard-simulated if no external test group is available, with the limitation recorded.
- (question) Exact numerical compendium content counts, derived-resource field breakdowns, and deeper enchantment/alchemy/ritual/combat sub-procedures remain focused downstream decisions.
- (event) Coherence validation passed: six stable capabilities have intent and success, constraints bend design, non-goals are explicit, success signal is demonstrable, assumptions and open questions are separated, and prose is lean.
- (event) Preservation validation passed: load-bearing detail remains in adopted companions for PRD requirements, rules checklist, UX behavior/design, architecture decisions, and project conventions; product brief is listed as fully absorbed source.
